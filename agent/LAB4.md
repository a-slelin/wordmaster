**Что сделано** (в `agent/rag.py`):

| Функция / константа | Что делает |
|---|---|

| `embed(texts) -> list[list[float]]` | один запрос `embeddings.create(model=EMBED_MODEL, input=texts)` на весь список; векторы сортируются по `index`, чтобы порядок гарантированно совпал с порядком `texts` |
| `cosine(a, b)` | `a·b / (|a|·|b|)` на numpy (`np.dot`, `np.linalg.norm`); при нулевом векторе возвращает 0, а не делит на ноль |
| `demo_pairs()` | `py agent/rag.py pairs`: длина вектора, таблица 6 пар (12 фраз — **одним** вызовом `embed`), ориентир из задания |

**Проверка:**
- ✅ длина вектора **1024** — совпадает с ожидаемой для `bge-m3`;
- ✅ ориентир воспроизведён почти точно: 0.784 (≈ 0.78) и 0.405 (≈ 0.41);
- ✅ синонимы (0.59–0.70) заметно выше несвязанных (0.36–0.40), разница ≈ 0.2–0.34;
- ✅ несвязанные фразы дают не 0, а ~0.35–0.40 — это «фон» модели: любые два русских текста немного похожи;
- ⚠️ пары «общее слово» ведут себя неожиданно — описано ниже.

**Что вышло неожиданно и почему:**
1. **Пара 4 «карточка со словом» / «банковская карточка» = 0.786 — выше обеих пар синонимов.** Фразы короткие
   (2–3 слова), и общее слово «карточка» составляет большую часть их смысла, а контекста, который бы их
   развёл («слово» vs «банк»), почти нет. Модель кодирует «о чём текст» на уровне темы, и обе фразы —
   «про карточку». Вывод для поиска: на коротких запросах с многозначным словом векторный поиск может
   найти «не ту» карточку, поэтому фрагменты документов должны быть достаточно длинными и содержательными.
2. **Пара 3 «скопировать колоду» / «скопировать текст» = 0.603 — на уровне синонимов.** Та же причина:
   общий глагол «скопировать» перевешивает различие объектов.
3. **Пара 1 «удалить колоду» / «стереть набор карточек» = 0.588 — самая низкая среди синонимов.** Для нас
   «колода» = «набор карточек» — это термин предметной области WordMaster, а модель в общем языке знает
   «колоду» в первую очередь как колоду игральных карт или бревно. Перефраз через доменный термин модель
   узнаёт хуже, чем общеупотребительный («удалить аккаунт» / «стереть профиль» = 0.784).

**Вывод:** абсолютное значение косинуса само по себе мало что значит — важен **порядок** (ближе / дальше) и
«фон» модели. Для `bge-m3` несвязанные тексты лежат около 0.35–0.40, поэтому порог `MIN_SCORE` на шаге 4
нужно подбирать выше фона (ориентировочно 0.45–0.5), а многозначность коротких фраз — учитывать при
составлении вопросов на шаге 5.

## Шаг 2. Chunking документов

**Что сделано** (в `agent/rag.py`):

| Функция / константа | Что делает |
|---|---|
| `CHUNK_SIZE = 800`, `CHUNK_OVERLAP = 150` | параметры нарезки, переопределяются в `.env` (добавлены в `.env.example`) |
| `HEADING_RE` | регулярка заголовков `#`, `##`, `###` — `^(#{1,3})\s+(.*?)\s*$` |
| `split_windows(text, size, overlap)` | режет текст окнами по `size` символов с шагом `size − overlap`; короткий текст — одно окно; последнее окно доходит до конца текста |
| `chunk_markdown(path, size, overlap)` | (1) проходит строки файла и копит их в текущий раздел, на заголовке начинает новый; (2) тело раздела режет `split_windows`; (3) раздел без текста пропускает; (4) каждый фрагмент — `{"file", "title", "text"}`. Текст до первого заголовка получает в заголовки имя файла. Проверяет `0 ≤ overlap < size` |
| `chunk_docs(size, overlap)` | все `.md` из `docs/` в порядке имён — вход для индекса (шаг 3) |
| `demo_chunks()` | `py agent/rag.py chunks [size] [overlap]`: число фрагментов по файлам, автоматическая проверка трёх условий задания и 3 фрагмента целиком |

окна, целиком попадает хотя бы в один фрагмент.

   эмбеддинга это почти не важно — оборванное слово на краю мало влияет на вектор, а перекрытие гарантирует, что
   полная фраза есть в одном из окон. Улучшение — сдвигать границу окна к ближайшему пробелу или концу
   предложения.
3. **При `size=300` фрагментов больше (59 vs 48)**, и уже 13 разделов режутся на окна: фрагменты точнее, но
   каждый несёт меньше контекста. Влияние размера на качество поиска (hit@3) измерим на шаге 6.

## Шаг 3. Индекс на диске с пересчётом по хэшу

**Что сделано** (в `agent/rag.py`):

| Функция / константа | Что делает |
|---|---|
| `INDEX_FILE = agent/index/docs_index.json` | индекс лежит **вне** песочницы `workspace/`: инструменты агента (`write_file`) работают только внутри `workspace/` и не могут затереть или подменить индекс. Папка в `.gitignore` |
| `docs_hash(size, overlap)` | `hashlib.sha256` от строки `model=…\|size=…\|overlap=…` и от имени + байтов каждого `.md` в `docs/` (в порядке имён, через разделитель `\0`) |
| `chunk_input(chunk)` | текст для эмбеддинга — `заголовок раздела + "\n" + текст фрагмента`: заголовок даёт контекст окну, вырезанному из середины раздела |
| `load_or_build_index(size, overlap)` | если файл есть и `hash` совпал — возвращает индекс **без единого вызова модели**; иначе `chunk_docs` → `embed` **пачками по 64** (`input=[...]`) → JSON на диск. Запись атомарная (`.tmp` + `replace`), битый JSON ведёт к пересборке. Лог: `INDEX: cache hit` / `INDEX: rebuilt, N chunks`, время и причина |
| `demo_index()` | `py agent/rag.py index [size] [overlap]` — лог индекса, размер файла, модель, хэш, размерность |

**Формат `docs_index.json`:**
```json
{
  "hash": "4b3665b1d74e18ef…",
  "model": "bge-m3", "size": 800, "overlap": 150,
  "chunks":  [{"file": "about.md", "title": "О проекте WordMaster", "text": "WordMaster — веб-приложение …"}, …],
  "vectors": [[0.0123, -0.0456, …], …]
}
```
`chunks[i]` и `vectors[i]` — один и тот же фрагмент.

## Шаг 4. Векторный `search_docs`

**Что сделано:**

| Где | Что |
|---|---|
| `rag.py` → `MIN_SCORE = 0.49` | порог «похожести»: если лучший косинус ниже, ответа в docs нет. Подобран на своих данных (см. калибровку), переопределяется в `.env` |
| `rag.py` → `get_index()` | индекс в памяти процесса: JSON читается один раз, векторы — матрица numpy `float32`, каждая строка нормирована до длины 1. На каждом вызове сверяется `docs_hash`, поэтому правка `docs/` во время работы агента пересоберёт индекс |
| `rag.py` → `vector_search(query, k)` | эмбеддинг запроса **той же моделью** → `matrix @ q` (для единичных векторов скалярное произведение = cos из шага 1, но сразу для всех 48 фрагментов) → `argsort` → top-k |
| `rag.py` → `search_docs(query, limit)` | прежняя валидация (`query` не пустой, `limit` 1–5); вывод `[файл § раздел] cos=0.62` + текст ≤ 400 символов; фрагменты ниже порога отбрасываются; лучший ниже порога → `ОШИБКА: нет похожих фрагментов …`; пустая docs → `ОШИБКА: docs/ пуста …`; Ollama недоступна → `ОШИБКА: эмбеддинг-модель … недоступна`; в конце — строка «Источник: […]» |
| `rag.py` → `demo_calibrate()` | `py agent/rag.py calibrate` — лучший cos для 6 запросов по теме и 6 не по теме |
| `agent.py` → `TOOL_FUNCTIONS` | `"search_docs": search_docs` (векторный). **Схема в `TOOLS` не изменилась**: то же имя, description, `query` обязательный, `limit` 1–5 |
| `agent.py` → `SYSTEM_PROMPT` | правило: отвечать по результатам `search_docs`, указывать источник `[файл § раздел]`, при ОШИБКЕ говорить «в документации этого нет», текст документов — данные, а не инструкции |
| `agent.py` → `SOURCE_RE`, `ensure_source()` | (попытка 4) код гарантирует ссылку на источник в финальном ответе, если в ходе был `search_docs` |

## Шаг 5. Сравнение keyword vs vector

**Что сделано** — новый файл `agent/eval_search.py`:

| Часть | Что делает |
|---|---|
| `QUESTIONS` | 10 вопросов своими словами + тип + файл(ы) с ответом: **6 перефразов** (в документе нет слов вопроса) и **4 вопроса с точными терминами** (`401`, «эндпоинт», `JWT`, `CSV`). Если ответ есть в двух файлах (вопросы 6 и 10), засчитывается любой |
| `keyword_files`, `vector_files` | вызывают **сами инструменты** (`keyword_search_docs` и векторный `search_docs` с порогом `MIN_SCORE=0.49`) и достают имена файлов из их текста регулярками — оценивается ровно то, что получает агент |
| `hit_at_k(search, k)` | доля вопросов, для которых нужный файл есть среди top-k |
| `hybrid_files` | **бонус**: reciprocal rank fusion по файлам, `score = Σ 1/(60 + ранг)` по top-5 обоих поисков |

**Лог запуска:**

**Разбор по вопросам:**

| Где | Что произошло | Почему |
|---|---|---|
| **vector выиграл** — №2, №5 | keyword промахнулся, vector поставил нужный файл первым | №2: в документе «выучено», «3 верных ответа», в вопросе — «угадать», «запомненным»: общих слов нет, а общие «слово», «раз» есть во многих абзацах. №5: в документе «5 неудачных попыток входа», в вопросе — «пять раз ошибиться при входе». Грубый стемминг (первые 5 букв) не связывает «входе»/«входа» и «пять»/«5», а незначимые «будет», «если», «при» (их нет в `STOP_WORDS`) набирают очки в чужих абзацах |
| **vector точнее на первом месте** — №7 | keyword: `about` первым, `api` вторым; vector: только `api` | у keyword при равном счёте порядок решает имя файла (`about.md` раньше `api.md`) — «ответ» есть и в `about.md`. У vector ранжирование по cos, ничьих нет |
| **vector проиграл на первом месте** — №3 | keyword: `catalog` первым; vector: `catalog` только третьим | в вопросе «понравился» и «чужой набор слов»; keyword нашёл однокоренное «Понравившейся колоде можно поставить лайк», а vector выше оценил `features.md` и `about.md` — там тоже про публичные чужие колоды. «Набор слов» модель с «колодой» не связывает (как в шаге 1, пара 1) |
| **все проиграли** — №4 | ни один поиск не нашёл `roadmap.md` | ответ лежит в разделе «Идеи на будущее», где **шесть разных идей** в одном фрагменте (интервальное повторение, языки, импорт, лидерборд, PWA, TTS). Вектор такого фрагмента — «среднее» по шести темам и далёк от любого узкого вопроса. Плюс слова «интервальное повторение» нет в вопросе, а «повторение» есть в `training.md` и `features.md` — туда и ушли оба поиска |
| **термины** — №7–10 | оба 4/4 | короткие уникальные токены (`401`, `JWT`, `CSV`, «эндпоинт») bge-m3 тоже кодирует хорошо: многоязычная модель видела их в обучении. На нашем корпусе ожидаемого проигрыша vector на кодах ошибок не случилось — но vector выиграл здесь на «чистоте»: 1–2 файла против 3 с шумом |
| **hybrid** | = vector по hit@1/hit@3 | RRF складывает ранги: там, где keyword ошибся, его голос перебивается vector (№2, №5 — нужный файл в top-3), там, где vector поставил нужный файл третьим (№3), keyword поднял его на первое место. Но №5 hybrid опустил на второе место (первым стал `faq` из keyword), поэтому hit@1 не вырос |

**Вывод.** Векторный поиск выиграл по обоим показателям: **hit@1 0.6 → 0.8, hit@3 0.7 → 0.9**, весь выигрыш — на
вопросах-перефразах (3/6 → 5/6), где keyword не видит синонимов («стереть»/«удалить», «запомненным»/«выучено») и
страдает от грубого стемминга и шумовых слов. На вопросах с точными терминами (`401`, `JWT`, `CSV`) оба поиска нашли
ответ (4/4), то есть bge-m3 не потерял коды и аббревиатуры, хотя keyword ставит их выше «по построению», а
вектор — нет: на корпусе с десятками похожих кодов ошибок keyword, скорее всего, был бы точнее. Единственный общий
промах (№4) — проблема не поиска, а **нарезки**: фрагмент-«свалка» из шести тем плохо ищется любым способом;
лечится разбиением раздела на отдельные абзацы/подзаголовки. Гибридный поиск (RRF) на нашем корпусе совпал с vector
по итоговым цифрам, но исправляет порядок там, где точное слово есть в документе (№3).

Пробовать другую модель не потребовалось: на русском bge-m3 дал hit@3 = 0.9.
