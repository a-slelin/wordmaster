## Шаг 1. Сессия на диске

### Что сделано

| Функция / место                | Что делает                                                                              |
|--------------------------------|-----------------------------------------------------------------------------------------|
| `--session <id>` / `SESSION_ID` | выбор сессии через `argparse`, по умолчанию `default`                                  |
| `session_path(id)`             | путь `agent/sessions/<id>.json`; id проверяется регуляркой `^[A-Za-z0-9_-]{1,64}$`     |
| `save_session(id, messages)`   | сохраняет историю **без** system, через временный файл и `replace()`                    |
| `load_session(id)`             | читает историю и ставит свежий `SYSTEM_PROMPT` первым сообщением                        |
| `run_agent(..., on_step)`      | колбэк сохранения после каждого шага с инструментами                                    |
| `main()`                       | сохраняет после вопроса пользователя и после финального ответа                          |

### Решения и почему

1. **System-промпт не хранится в файле.** При загрузке он всегда добавляется ровно один раз из кода, поэтому
   задвоиться не может. Плюс: если поправить промпт в коде, изменение сразу действует и в старых сессиях.
2. **Проверка id сессии.** Без неё `--session ../../.env` превратился бы в путь вне `sessions/`. Это та же идея,
   что `safe_path` для песочницы в лаб. 2.
3. **Атомарная запись** (`.tmp` → `replace`). Если прервать программу во время записи, старый файл останется
   целым и не превратится в обрезанный JSON, который потом не загрузится.
4. **Когда сохраняем.** Сразу после вопроса (он не потеряется, даже если упадёт API), после каждого шага агента
   и после финального ответа. Шаг с инструментами сохраняется только когда **все** результаты `role: tool`
   уже в истории. Иначе в файле мог бы остаться `tool_calls` без ответов, и такая история не прошла бы
   валидацию API при следующем запуске.
5. **Секреты в файл не попадают.** Сохраняется только список `messages`, ключ из `.env` в него никогда не входит.
   Файлы `sessions/*.json` в `.gitignore`.

## Шаг 2. Оценка размера контекста

### Что сделано

| Место                             | Что делает                                                                                  |
|-----------------------------------|---------------------------------------------------------------------------------------------|
| `estimate_tokens(messages, tools)` | `len(json.dumps(messages) + json.dumps(tools)) // 4` — грубая оценка токенов               |
| `run_agent`, до запроса           | печатает `оценка до запроса: ~N ток. (K сообщений)`                                         |
| `run_agent`, после ответа         | печатает `usage: prompt=…, completion=…` и отношение `оценка/факт`                          |

Почему так:

1. **Считаем весь JSON, а не только `content`.** В запрос уходят `tool_calls` с аргументами, `tool_call_id`, роли
   и описания `TOOLS`, и всё это тоже стоит токенов. `TOOLS` отправляются в **каждом** запросе.
2. **Оценка до запроса нужна для шага 3.** `usage` известен только **после** ответа, а решать, обрезать ли
   историю, нужно **до** него.
3. **`if usage and usage.prompt_tokens`.** Бесплатные модели на OpenRouter иногда не возвращают `usage`, и
   программа не должна из-за этого падать.

## Шаг 3. Бюджет и усечение

### Что сделано

| Место                           | Что делает                                                                                     |
|---------------------------------|------------------------------------------------------------------------------------------------|
| `CONTEXT_BUDGET`                | бюджет в «условных токенах» `estimate_tokens`, по умолчанию 6000, задаётся через `.env`/переменную |
| `split_turns(messages)`         | делит историю на голову (system в начале) и **ходы**: `user` + все его `assistant`/`tool`      |
| `ensure_context_budget(messages)` | пока оценка > бюджета, удаляет самый старый ход **целиком**; пишет `TRIM: removed …`         |
| `run_agent`                     | вызывает `ensure_context_budget` перед **каждым** запросом к API                               |

### Решения и почему

1. **Единица удаления — ход, а не сообщение.** Ход начинается с `user` и содержит все `assistant` с
   `tool_calls` и их `role: tool`. Если удалять ход целиком, `tool` без своего `tool_calls` остаться не может,
   и история всегда валидна для API. Если удалять по одному сообщению, можно отрезать `assistant` с
   `tool_calls` и оставить его ответы `tool`, и тогда запрос упадёт с ошибкой 400.
2. **Что не трогаем никогда:** system (он в «голове») и последний ход, то есть текущую задачу вместе с её
   tool-циклом (условие `len(turns) > 1`).
3. **Не падаем.** Если даже без старых ходов бюджет превышен (огромный результат tool в текущем ходе), пишем
   предупреждение и отправляем запрос как есть.
4. **Вызов перед каждым запросом, а не перед каждым вопросом**, потому что контекст растёт как раз внутри
   tool-цикла: один `read_file` добавил ~260–320 токенов.
5. **`messages[:] = …`** заменяет содержимое того же списка, который держат `main()` и `save_session`, поэтому
   на диск сохраняется уже усечённая история. Обычное присваивание `messages = …` создало бы новый локальный
   список, и обрезка не дошла бы ни до сессии, ни до следующих шагов.

### Токены: без обрезки (шаг 2) и с обрезкой (шаг 3)

Те же вопросы; в шаге 3 первым идёт ещё ход «Меня зовут Александр», так что без обрезки он был бы даже больше.

| Вызов                           | Шаг 2 (без бюджета): оценка / prompt | Шаг 3 (бюджет 1300): оценка / prompt | Экономия prompt |
|---------------------------------|-------------------------------------:|-------------------------------------:|----------------:|
| `faq.md`, запрос с tool_call    | 1359 / 1752                          | 1183 / 1597 (TRIM)                   | −9 %            |
| `faq.md`, ответ после tool      | 1624 / 2026                          | 928 / 1288 (TRIM)                    | −36 %           |
| карточка, запрос с tool_call    | 1809 / 2246                          | 1104 / 1490                          | −34 %           |
| карточка, ответ после tool      | 1905 / 2314                          | 1200 / 1558                          | −33 %           |

### Наблюдения

- **Обрезка сработала дважды за один вопрос, и второй раз — посреди tool-цикла:** после `read_file(faq.md)`
  оценка выросла до 1447 > 1300, и удалился ход про `training.md`. Текущий ход (`user` → `assistant` с
  `tool_calls` → `tool`) остался целым, запрос к API прошёл, модель нормально ответила по `faq.md`.
- **Удаляется больше, чем «одно сообщение».** В первый раз удаления одного хода (приветствие, ~35 токенов) не
  хватило, и ушёл ещё ход с `list_files`: 2 хода / 6 сообщений.
- **Без обрезки контекст рос бы линейно, с обрезкой он держится у бюджета:** оценка колеблется в диапазоне
  ~930–1230 и не растёт. Реальный `prompt_tokens` при этом ~1300–1600, то есть выше бюджета, потому что бюджет
  задан в единицах нашей оценки, а она занижает (см. шаг 2).
- **Минус trim — потеря фактов.** На «Как меня зовут?» агент честно ответил «Я не знаю», потому что ход с
  именем удалён и из памяти, и из файла сессии. Это и есть мотивация для шага 4.
- **Возможное улучшение:** обрезка «до самой границы» бюджета приводит к тому, что следующий же вопрос
  снова её запускает (TRIM на двух вызовах подряд). Можно резать с запасом, например до 70 % бюджета, чтобы
  обрезки случались реже.
